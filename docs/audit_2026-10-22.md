# Audit of the repeat calculations and comparison with other MLVA tools

Date: 2026-10-22. This audit covers mlvatyper 0.1.0, the state before the
allele caller was added in 0.2.0. The section "What changed in 0.2.0" at the
end maps the findings to the current implementation.


## Short answer

The repeat calculations are not robust enough for allele calling. Both
estimators reproduce the legacy script, which was a sequence-extraction and
alignment aid, not an allele caller. Specifically:

- `count_repeats` (summarize.py) counts exact, non-overlapping, strand-specific
  substring matches anywhere in the amplicon. Imperfect repeat units (one
  substitution or indel) are not counted, so arrays with variant units are
  undercounted. Several patterns are summed independently (double counting
  when one pattern contains another). The reverse complement is never tried.
  Tandem arrangement is not required, so short AT-rich units match flank
  sequence by chance.
- `length_diff_from_shortest_table` divides (length - shortest length of that
  marker in the current run) by the unit length. The reference is therefore
  the shortest amplicon in the dataset: the values change when samples are
  added or removed, are not comparable between runs, and cannot be mapped to
  MLVAbank allele numbers. Values are printed with three decimals and never
  rounded or flagged, so flanking indels or a wrong unit length pass unnoticed.
- No pattern file exists in the project, so the counting path has never been
  run on real data. A probe over out_test/hits.tsv (203 amplicons, one
  genome) found 41 local tandem arrays of 2.5 or more copies; in 35 of these
  exact counting returned fewer copies than the array span implies because
  the arrays contain mismatches.

## Other findings in the code

1. merPCR (engine.py:733-808) searches the reverse primer only within
   expected_size +/- margin. For VNTRs the true size depends on copy number,
   so the STS expected size and `-M` are the effective size window. The
   default 500 bp is permissive and global, not per marker.
2. merPCR appends one hit per matching reverse-primer position inside the
   window. A reverse primer that also matches inside or just after the array
   yields several hits for one locus; mlvatyper reports them as copies 1, 2,
   ... with no overlap-based deduplication and no ranking by mismatches.
3. Primer mismatch counts, the expected size and the deviation from it are
   not stored in hits.tsv, so ambiguous hits cannot be ranked or filtered.
4. A locus whose primers fall on different contigs, or near a contig end, is
   reported as NA, indistinguishable from a true deletion.
5. `three_prime_match` (merPCR default 1) is not exposed; `-N 3` per primer
   is permissive for 18 to 22 bp primers.
6. The pattern file is not validated against the STS ids, and the optional
   unit length column is not checked against the pattern lengths.
7. has_N is the only quality flag; no censoring for arrays that approach the
   assembly k-mer or read length (assembly collapse).
8. Minor: `pattern_counts_table` logs at info level for every marker without
   amplicons; column order of the count tables follows the pattern file, the
   lengths table is sorted.

## Comparison with the four named repositories

dpchris/MLVA and i2bc/MLVA_finder are the same script (one character
differs). Summary:

| Tool | Primer search | Repeat number | Reference needed | Non-integer handling | Multiple hits |
|---|---|---|---|---|---|
| MLVA_finder (dpchris = i2bc) | exact, then `regex` fuzzy with edit distance escalated 0..n per locus; IUPAC expanded; second primer searched genome-wide | `ref_allele + (size - ref_size) / unit`, size from nominal primer lengths; circular aware | yes, per locus in the primer name: unit bp, reference product bp, reference allele; optional bin table (Brucella v3.6) | snap to integer within +/-0.25 (`-r`), otherwise `n.5` intermediate allele | pair with smallest allele kept; contigs listed |
| MLVA_normalizer | none (capillary sizes in) | corrected length matched to reference strain lengths within +/-2 bp | yes, panel of reference strains | `check( ]a;b[ )` strings; -2 for no product | two-unit loci as 2+2 digit code |
| wgsMLVA | exact regex, hard-coded primers, last hit kept; closed genomes only | `fragment.count(unit)` plus variant units for VNTR1 | hard-coded type 27 lengths | fails `(len - ref) % unit == 0`: error text, locus omitted | VNTR3 duplication masked to PCR convention |
| mlvatyper (current) | merPCR, `-N` mismatches, size window `-M` | exact count of pattern; (len - shortest in run) / unit | none | three decimals, no flag | copies joined with `/` or `;`, no dedup |

Observations:
- Every comparable tool anchors the repeat number to a reference (reference
  strain product size and allele, allele table, or bin table). mlvatyper is
  the only one whose number depends on the dataset.
- MLVA_finder and wgsMLVA both treat a non-integer result as a signal
  (intermediate allele or error). mlvatyper prints it silently.
- wgsMLVA shows that pattern counting needs variant units even for a
  well-studied scheme (only 5 of 8 VNTR1 repeats were exact).
- MLVA_finder computes the size from nominal primer lengths at the matched
  positions, so primer indels do not shift the allele; mlvatyper inherits
  this correctly from merPCR, which does not allow primer indels at all.
- Weaknesses to avoid from the others: `seq.find(hit)` position recovery,
  keeping only the last hit, genome-wide second-primer search, string
  containment lookups against a type database.

## Comparison with the wider field

- MIRU-VNTR (MIRUReader, MIRU-profiler): allele calling by nearest entry in a
  per-locus size table, MIRU-profiler with an explicit +/-5 bp tolerance,
  fewest primer mismatches as tie-break, `NOT_DETECTED` and
  `UNKNOWN_ALLELE_NUM` as distinct codes. Locus 0580 has its own numbering.
- MISTReSS (Salmonella): blastn-short primer hits, size from outer primer
  edges, bins from an XML panel, NA when primers are on different contigs.
- MLVAtype (V. cholerae): the only motif-counting tool; works because the
  arrays are perfect and flanks lack indels, and the authors state it cannot
  be used for Brucella or Salmonella. It right-censors (`>=n`) when the array
  reaches the assembly k-mer capacity.
- PulseNet/BioNumerics: look-up table preferred; formula (size - offset) /
  unit only for new alleles.
- MLVAbank/Vergnaud convention: locus name `NAME_<unit>bp_<refsize>bp_<n>u`;
  expected size for n repeats = reference product + (n - n_ref) * unit.
- Rounding is not standardised between labs (Chalker et al. 2015: four labs
  round up, two down). The rule must be explicit and configurable, and a
  fractional value below 1 must never collapse to 0, because 0 is an allele.
- Dominant pitfalls: Illumina collapse of long tandem repeats (QUB26 missed
  in 61% of samples in MIRU-profiler), primers on different contigs, flanking
  indels, platform sizing offsets baked into legacy tables.

Conventions a comparable tool should follow: report copy numbers anchored to
a reference; prefer a per-locus table with tolerance, formula as fallback;
state the amplicon boundary convention; fixed and configurable rounding;
report raw evidence (length, residual in bp, mismatches, coordinates) next to
the call; distinct non-numeric codes for failure modes; flag rather than
silently resolve multiple hits; censor collapsed arrays; document the search
parameters in the output.


## What changed in 0.2.0

- Allele calling anchored to a reference (marker definition file, MLVAbank
  style ids, or a reference sample) with an explicit rounding policy and
  tolerance; see README, section Allele calling.
- Mismatch tolerant tandem array counting in both orientations as an
  independent estimate, with COUNT_DISAGREES when it differs from the length
  based allele.
- Overlapping hits for one locus are collapsed; primer mismatches, expected
  size, discarded alternatives and distance to the contig end are stored in
  hits.tsv.
- Primers near contig ends are detected for missing markers
  (NEAR_CONTIG_END).
- Text status codes instead of silent numbers, censoring option for
  collapsed arrays, run_info.json with all parameters.
- The legacy tables remain available with --legacy-tables.

## Cross-check against MLVA_finder (2026-10-23)

A synthetic dataset of 8 samples and 6 markers with planted repeat numbers
(0 to 10 copies, one missing locus, one locus with a 3 bp flank insertion,
one with a half unit partial repeat, two loci placed on the reverse strand,
one genome split into two contigs) was typed with mlvatyper 0.2.0
(`--markers` with patterns, reference values from the MLVAbank style ids)
and with MLVA_finder.py (i2bc, `-m 2 -c`). All 48 mlvatyper calls matched
the planted values, including the intermediate allele 4.5 and the missing
locus. MLVA_finder agreed on 47 of 48 calls. The one difference was the 3 bp
insertion in a 12 bp unit, raw value 4.25: mlvatyper reported 4 because its
tolerance was inclusive, MLVA_finder reports 4.5 because its comparison is
strict. mlvatyper now uses the strict comparison, so the two tools agree on
all 48 calls. The dataset generator is not part of the repository.

## Repeat unit discovery on the test genome (2026-10-23)

`mlvatyper discover` was run on the 203 amplicons of the test genome
(`/Users/andreassjodin/Desktop/test_pcr`, identical to the project copy).
With the default score threshold of 30 only one marker (testID208, TTGTT
times 4) shows a tandem array; 4 markers reach a score of 24, 11 reach 16
and 50 reach 12, the last group being mostly two copies of an AT-rich 6 to
8-mer or three copies of a trinucleotide, which is expected by chance in a
genome of this composition. The STS expected sizes equal the amplicon
lengths in this genome, so it is presumably the strain the primers were
designed on, and most loci hold one copy or a degenerate array there.
Repeat units for this primer set therefore cannot be derived from this
genome alone. They need either the scheme publication or discovery on
strains with more copies, after which `summarize --markers` with the
reviewed file calls alleles for all samples.

## Tandem Repeats Finder as discovery engine (2026-10-23)

`mlvatyper discover --engine trf` runs TRF 4.09.1 (bioconda) once on the
amplicons with the alignment parameters 2 7 7 80 10. On the synthetic
dataset TRF recovers all six planted units with the correct copy numbers.
On the test genome TRF reports arrays for 3 markers at its own default
minimum score of 50, 25 at score 30 and 89 at score 20. TRF scores every
base of the alignment to the consensus, so its scores run higher than the
built-in detector's for the same array, and two perfect copies of a 19 bp
unit reach 76. Most arrays found at score 30 are two to four copies of an
AT-rich 6 to 9 bp unit, and several have indels that the tandem counter
does not tolerate, so the counter's integer count can be lower than TRF's
fractional copy number; both are reported. The conclusion stands: this
genome holds few copies at most loci, and a sample with more copies or the
scheme publication is needed for the remaining units.

## Update 2026-10-23: merPCR 1.0.5

merPCR 1.0.5 reports `mismatches1`, `mismatches2`, `seq1` and `seq2` on
`SearchHit`, counted after the search with the comparison rule the search
used. mlvatyper now takes the primer mismatch counts from merPCR (mapping
the swapped primers of minus-strand records back to the STS forward and
reverse primer) and only counts them from the amplicon sequence for hits
without counts, such as rows read from an older `hits.tsv`. On the test
genome (203 amplicons, `-N 3`) the two sources give identical counts for
every hit. The search itself and the text output are unchanged upstream, so
hit coordinates and amplicon lengths are not affected.
